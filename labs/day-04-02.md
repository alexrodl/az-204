## 🧩 Introducción

Azure Cosmos DB es una base de datos distribuida globalmente que permite trabajar con distintos modelos de datos.

👉 No es una única base de datos, sino un servicio con múltiples APIs según el caso de uso.

---

## 🧱 APIs disponibles en Cosmos DB

### 🔹 API para NoSQL (Core / SQL)

- Modelo de documentos (JSON)
- API principal y más utilizada

👉 Caso de uso:
Aplicaciones web modernas (e-commerce, APIs, microservicios)

---

### 🔹 API para MongoDB

- Compatible con MongoDB
- Usa formato BSON

👉 Caso de uso:
Migración de aplicaciones existentes en MongoDB

---

### 🔹 API para Cassandra

- Modelo orientado a columnas

👉 Caso de uso:
IoT, telemetría, grandes volúmenes de datos

---

### 🔹 API para Table

- Modelo clave-valor

👉 Caso de uso:
Datos simples, configuraciones, logs

---

### 🔹 API para Gremlin

- Modelo de grafos

👉 Caso de uso:
Redes sociales, relaciones entre entidades

---

### 🔹 API para PostgreSQL

- Modelo relacional (SQL)

👉 Caso de uso:
Aplicaciones que requieren joins y transacciones complejas

---

## ⚖️ Comparación rápida

| API | Tipo de datos | Caso de uso |
|-----|-------------|------------|
| NoSQL | Documentos | Apps modernas |
| MongoDB | Documentos | Migraciones |
| Cassandra | Columnas | Big data / IoT |

# 🔄 Niveles de coherencia en Azure Cosmos DB

## 🧠 Introducción

La consistencia en Azure Cosmos DB define qué tan rápido los cambios realizados en los datos son visibles para las lecturas.

👉 Existe un balance entre:
- consistencia
- rendimiento
- latencia

Azure Cosmos DB ofrece 5 niveles de coherencia.

---

# 🔒 Strong Consistency

## ✅ Características

- Todos los clientes ven inmediatamente el dato más reciente
- Máxima consistencia
- Garantiza lecturas totalmente actualizadas

## 💡 Ejemplo

### Sistema bancario

Si un usuario realiza una transferencia:

```text
Saldo anterior: 100 USD
Saldo actual: 50 USD
```

👉 Todos los usuarios deben ver el nuevo saldo inmediatamente.

## 🎯 ¿Por qué usarlo?

Porque no se puede tolerar información desactualizada.

## ⚠️ Desventajas

- Mayor latencia
- Menor rendimiento
- Más costo operativo

---

# 🔄 Bounded Staleness

## ✅ Características

- Permite un pequeño retraso controlado
- Balance entre consistencia y rendimiento
- Los datos pueden retrasarse una cantidad limitada de tiempo o versiones

## 💡 Ejemplo

### Sistema de stock en e-commerce

Si alguien compra un producto:

```text
Stock actual: 5 unidades
```

👉 Puede tardar unos segundos en actualizarse globalmente, pero dentro de un límite controlado.

## 🎯 ¿Por qué usarlo?

Porque se puede tolerar un pequeño delay, pero limitado.

## 💡 Ejemplo conceptual

```text
Máximo retraso:
- 5 segundos
o
- 100 versiones
```

---

# 🧠 Session Consistency

## ✅ Características

- El usuario siempre ve sus propios cambios
- Otros usuarios podrían verlos un poco después
- Es el nivel por defecto en Cosmos DB

## 💡 Ejemplo

### Red social

Un usuario publica un comentario.

👉 El usuario lo ve inmediatamente.  
👉 Otros usuarios podrían verlo unos segundos después.

## 🎯 ¿Por qué usarlo?

Ofrece muy buen balance entre experiencia y rendimiento.

## 💡 Caso típico

- aplicaciones web
- APIs modernas
- aplicaciones móviles

---

# 📖 Consistent Prefix

## ✅ Características

- Mantiene el orden de los cambios
- Nunca se leen datos fuera de secuencia
- Puede faltar información reciente, pero nunca desordenada

## 💡 Ejemplo

### Sistema de logs o eventos

Eventos generados:

```text
A → B → C
```

👉 Nunca se verá:

```text
A → C
```

👉 El orden siempre se mantiene.

## 🎯 ¿Por qué usarlo?

Porque el orden de los eventos es importante.

## 💡 Caso típico

- logs
- procesamiento de eventos 
- auditoría

---

# ⚡ Eventual Consistency

## ✅ Características

- Máximo rendimiento
- Menor latencia
- Los datos eventualmente se sincronizan

## 💡 Ejemplo

### Likes en redes sociales

Un post tiene:

```text
100 likes
```

Otro usuario agrega un like.

👉 Durante unos segundos algunos usuarios podrían seguir viendo:

```text
100 likes
```

👉 Más adelante todos verán:

```text
101 likes
```

## 🎯 ¿Por qué usarlo?

Porque no es crítico tener el dato exacto inmediatamente.

## 💡 Caso típico

- likes
- métricas
- contadores
- analytics

---

# 📌 Resumen

| Nivel | Caso típico |
|------|-------------|
| Strong | banca |
| Bounded Staleness | stock |
| Session | apps web |
| Consistent Prefix | logs/eventos |
| Eventual | likes/redes sociales |

# 🔥 Consistencia por defecto vs por request

## 🧠 Introducción

Cuando se crea una cuenta de Cosmos DB, se define un nivel de consistencia por defecto.

Ejemplo:

```text
Session
```

👉 Todas las operaciones usarán ese nivel por defecto.

---

# 🔄 Override por request/query

Desde el SDK es posible modificar el nivel de consistencia para una operación específica.

👉 Esto NO se configura por documento/item.

👉 Se configura por Operación de lectura:
- request
- query

---

# 💡 Ejemplo conceptual

## Configuración default

```text
Cuenta Cosmos:
→ Session
```

## Lectura normal

```text
Feed de noticias:
→ Session
```

## Lectura menos crítica

```text
Likes:
→ Eventual
```

👉 Esto mejora rendimiento y reduce latencia.

---

# ⚠️ Importante

No es posible solicitar un nivel de consistencia más fuerte que el configurado en la cuenta.

## ❌ Ejemplo inválido

```text
Cuenta:
→ Session

Request:
→ Strong
```

👉 Esto no es permitido.

---

# 💡 Analogía

👉 La cuenta define la velocidad máxima permitida.

👉 Cada request decide si quiere usar un nivel menor de consistencia.

---

# 📌 Resumen final

- La consistencia define qué tan actualizados están los datos
- Mayor consistencia generalmente implica:
  - más latencia
  - menor rendimiento
- Menor consistencia generalmente implica:
  - más velocidad
  - mejor escalabilidad
- El nivel por defecto se configura en la cuenta
- Puede modificarse por request/query
- No puede configurarse por item/documento
